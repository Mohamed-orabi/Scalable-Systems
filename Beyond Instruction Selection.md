# Chapter 13: Beyond Instruction Selection — A Comprehensive Explanation

## Overview and Context

This chapter moves beyond the instruction selection mechanisms (Selection DAG and GlobalISel) covered in Chapters 11–12 and explores three important topics that complete the picture of a working compiler backend:

1. **Adding a new machine function pass** — how to write custom optimization or transformation passes that run on machine code *after* instruction selection.
2. **Integrating a new target into the Clang frontend** — how to teach Clang (the C/C++ compiler frontend) about the M88k architecture so users can compile C code directly for M88k.
3. **Cross-compiling** — how to build programs on one architecture (e.g., x86_64) that run on a completely different architecture (e.g., AArch64/ARM).

All three topics continue using the Motorola 88000 (M88k) architecture as the running example.

## Part I: Adding a New Machine Function Pass to LLVM

### What Is a Machine Function Pass?

In LLVM, there are two worlds of passes:

- **IR-level passes** operate on LLVM IR (the target-independent intermediate representation). These are the passes you run with `opt` — things like dead code elimination, loop unrolling, constant propagation, etc. They work on the `Function` class and override `runOnFunction()`.

- **Machine function passes** operate on the `MachineFunction` representation — the target-specific, post-instruction-selection representation that contains actual machine instructions, physical/virtual registers, and machine basic blocks. These run within `llc` (the LLVM static compiler) and override `runOnMachineFunction()`.

A `MachineFunctionPass` is a subclass of `FunctionPass` that has been adapted to work with `MachineFunction` instead of `Function`. It processes one machine function at a time.

### Important Note About Pass Managers

The chapter explicitly states that LLVM's backend **still uses the legacy pass manager**, not the new pass manager. The new pass manager has not been fully implemented for the backend yet. Therefore, all the pass registration and initialization code in this chapter follows the legacy pass manager's conventions (using `INITIALIZE_PASS`, `PassRegistry`, static `char ID`, etc.).

### The Purpose of This Specific Pass

The pass being implemented is called **`M88kDivInstr`**. Its purpose is to detect division instructions and insert **division-by-zero checks** — specifically, a conditional branch and a trap instruction that will cause the CPU to halt if a division by zero is attempted.

**Why is this needed?** The MC88100 CPU (the first-generation M88k processor) has a hardware limitation: it does not reliably detect division-by-zero situations on its own. So the compiler must insert explicit checks in software. This is a perfect example of a target-specific concern that can't be handled at the IR level — it needs to happen after instruction selection, when we know exactly which machine instructions are present.

### Step 1: Declaring the Pass Interface (M88k.h)

In the main header file for the M88k target (`llvm/lib/Target/M88k/M88k.h`), two function prototypes are added inside the `llvm` namespace:

```cpp
void initializeM88kDivInstrPass(PassRegistry &);
FunctionPass *createM88kDivInstr(const M88kTargetMachine &);
```

The first function is the **initialization function**. Every legacy pass in LLVM needs an initialization function that registers the pass with LLVM's `PassRegistry` — a central registry that tracks all known passes, their names, dependencies, and properties. This function is generated by the `INITIALIZE_PASS` macro but must be declared here so other files can call it.

The second function is a **factory function** — the standard LLVM pattern for creating pass instances. Rather than exposing the pass class itself, you expose a function that creates and returns one. This enables the pass to be defined in an anonymous namespace (limiting its visibility) while still being creatable from outside.

### Step 2: Integrating the Pass into the Target Machine (M88kTargetMachine.cpp)

#### Adding a Command-Line Toggle

LLVM has a built-in command-line option parsing system (`cl::opt`). A boolean option is declared:

```cpp
static cl::opt<bool>
    NoZeroDivCheck("m88k-no-check-zero-division", cl::Hidden,
                   cl::desc("M88k: Don't trap on integer division by zero."),
                   cl::init(false));
```

Breaking this down:
- **`cl::opt<bool>`**: A command-line option of type boolean.
- **`"m88k-no-check-zero-division"`**: The name as it appears on the command line (e.g., `--m88k-no-check-zero-division`).
- **`cl::Hidden`**: This option won't appear in `--help` by default — only in `--help-hidden`. This is used for options that most users don't need to know about.
- **`cl::desc(...)`**: A human-readable description.
- **`cl::init(false)`**: The default value is `false`, meaning the division-by-zero check is **enabled** by default. The user must explicitly pass this flag to *disable* the check.

This is wrapped in a method:

```cpp
bool M88kTargetMachine::noZeroDivCheck() const { return NoZeroDivCheck; }
```

This method is also declared in `M88kTargetMachine.h` so it can be queried from the pass implementation.

#### Registering the Pass

Inside `LLVMInitializeM88kTarget()`, the pass initialization is added:

```cpp
extern "C" LLVM_EXTERNAL_VISIBILITY void LLVMInitializeM88kTarget() {
    RegisterTargetMachine<M88kTargetMachine> X(getTheM88kTarget());
    auto &PR = *PassRegistry::getPassRegistry();
    initializeM88kDAGToDAGISelPass(PR);
    initializeM88kDivInstrPass(PR);  // NEW: register our pass
}
```

This ensures the pass is known to the framework before it's ever added to a pipeline.

#### Adding the Pass to the Pipeline

The pass is added as a **machine SSA optimization** — meaning it runs while machine instructions are still in Static Single Assignment form (before register allocation destroys SSA):

```cpp
void M88kPassConfig::addMachineSSAOptimization() {
    addPass(createM88kDivInstr(getTM<M88kTargetMachine>()));
    TargetPassConfig::addMachineSSAOptimization();
}
```

The call to the parent's `addMachineSSAOptimization()` ensures all the standard machine SSA optimization passes still run. Our pass is inserted *before* them, so it runs first.

The method `addMachineSSAOptimization()` is overridden in `M88kPassConfig` alongside `addInstSelector()` and `addPreEmitPass()`.

#### Debug Type and Statistics

```cpp

```

`DEBUG_TYPE` enables fine-grained debugging. When you run `llc -debug-only=m88k-div-instr`, only debug output from this pass will be shown. This is essential for debugging one pass in isolation without being overwhelmed by output from the entire compilation pipeline.

```cpp

```

`STATISTIC` declares a counter that tracks how many division-by-zero checks were inserted. You can view these statistics by running `llc -stats`. This is valuable for understanding how often the pass fires and for regression testing.

#### Condition Codes Enum

```cpp
enum class CC0 : unsigned {
    EQ0 = 0x2,   // Equal to zero
    NE0 = 0xd,   // Not equal to zero
    GT0 = 0x1,   // Greater than zero
    LT0 = 0xc,   // Less than zero
    GE0 = 0x3,   // Greater than or equal to zero
    LE0 = 0xe    // Less than or equal to zero
};
```

The M88k architecture has a conditional branch instruction (`BCND`) that branches based on comparing a register to zero using these condition codes. The hex values are the actual hardware encodings. The pass will use `NE0` (not equal to zero) — meaning "branch if the divisor is not zero" (skip the trap).

#### The M88kDivInstr Class

```cpp
class M88kDivInstr : public MachineFunctionPass {
    friend class M88kBuilder;
    const M88kTargetMachine *TM;
    const TargetInstrInfo *TII;
    const TargetRegisterInfo *TRI;
    const RegisterBankInfo *RBI;
    MachineRegisterInfo *MRI;
    bool AddZeroDivCheck;
```

Members explained:
- **`friend class M88kBuilder`**: Allows the builder class to access private members of this pass (specifically `TII`, `TRI`, `RBI`).
- **`TM`**: The target machine — provides access to the command-line toggle.
- **`TII`**: Target instruction information — needed to look up instruction descriptors by opcode.
- **`TRI`**: Target register information — needed for register constraint checking.
- **`RBI`**: Register bank information — needed for GlobalISel register bank constraints.
- **`MRI`**: Machine register information — tracks virtual registers in the current function.
- **`AddZeroDivCheck`**: Whether the pass should actually insert checks (derived from the command-line option).

Public interface:

```cpp
public:
    static char ID;
    M88kDivInstr(const M88kTargetMachine *TM = nullptr);
    MachineFunctionProperties getRequiredProperties() const override;
    bool runOnMachineFunction(MachineFunction &MF) override;
    bool runOnMachineBasicBlock(MachineBasicBlock &MBB);
private:
    void addZeroDivCheck(MachineBasicBlock &MBB, MachineInstr *DivInst);
};
```

- **`static char ID`**: Every legacy pass needs a unique static ID. The address of this variable is used as a unique identifier — it doesn't matter what value it holds.
- **`getRequiredProperties()`**: Specifies what properties the machine function must have for this pass to run. This pass requires **SSA form**.
- **`runOnMachineFunction()`**: The main entry point — called once per machine function.
- **`runOnMachineBasicBlock()`**: A helper that processes one basic block at a time.
- **`addZeroDivCheck()`**: The core logic that inserts the check around a specific division instruction.

#### The M88kBuilder Helper Class

This is a specialized builder for constructing M88k-specific machine instructions:

```cpp
class M88kBuilder {
    MachineBasicBlock *MBB;
    MachineBasicBlock::iterator I;
    const DebugLoc &DL;
    const TargetInstrInfo &TII;
    const TargetRegisterInfo &TRI;
    const RegisterBankInfo &RBI;
```

It wraps the standard `BuildMI` infrastructure with M88k-specific convenience methods.

The constructor initializes from the pass:

```cpp
M88kBuilder(M88kDivInstr &Pass, MachineBasicBlock *MBB, const DebugLoc &DL)
    : MBB(MBB), I(MBB->end()), DL(DL), TII(*Pass.TII),
      TRI(*Pass.TRI), RBI(*Pass.RBI) {}
```

The iterator `I` is set to `MBB->end()`, meaning new instructions will be appended at the end of the block.

**`constrainInst()`**: After building a machine instruction, this method ensures that the register operands are properly constrained to valid register classes:

```cpp
void constrainInst(MachineInstr *MI) {
    if (!constrainSelectedInstRegOperands(*MI, TII, TRI, RBI))
        llvm_unreachable("Could not constrain register operands");
}
```

`constrainSelectedInstRegOperands` is a framework function that checks each register operand and ensures it belongs to a valid register class for that instruction. If it can't be constrained, something is fundamentally wrong.

**`bcnd()` — Build a conditional branch:**

```cpp
MachineInstr *bcnd(CC0 Cc, Register Reg, MachineBasicBlock *TargetMBB) {
    MachineInstr *MI = BuildMI(*MBB, I, DL, TII.get(M88k::BCND))
                           .addImm(static_cast<int64_t>(Cc))
                           .addReg(Reg)
                           .addMBB(TargetMBB);
    constrainInst(MI);
    return MI;
}
```

This creates a `BCND` (conditional branch) instruction with three operands: the condition code (as an immediate), the register to test, and the target basic block. On M88k, `BCND` compares a register against zero and branches based on the condition.

**`trap503()` — Build a trap instruction:**

```cpp
MachineInstr *trap503(Register Reg) {
    MachineInstr *MI = BuildMI(*MBB, I, DL, TII.get(M88k::TRAP503))
                           .addReg(Reg);
    constrainInst(MI);
    return MI;
}
```

`TRAP503` raises trap vector 503 if the 0th bit of the register is not set. This is the M88k's mechanism for triggering a software trap — essentially a controlled crash that the operating system can catch and handle (typically by sending a signal to the process).

#### The Core Logic: addZeroDivCheck()

```cpp
void M88kDivInstr::addZeroDivCheck(MachineBasicBlock &MBB,
                                    MachineInstr *DivInst) {
    assert(DivInst->getOpcode() == M88k::DIVSrr ||
           DivInst->getOpcode() == M88k::DIVUrr && "Unexpected opcode");
    MachineBasicBlock *TailBB = MBB.splitAt(*DivInst);
    M88kBuilder B(*this, &MBB, DivInst->getDebugLoc());
    B.bcnd(CC0::NE0, DivInst->getOperand(2).getReg(), TailBB);
    B.trap503(DivInst->getOperand(2).getReg());
    ++InsertedChecks;
}
```

This is the heart of the pass. Here's what happens step by step:

1. **Assert**: Verify we're looking at a division instruction (`DIVSrr` for signed division, `DIVUrr` for unsigned division).

2. **Split the basic block**: `MBB.splitAt(*DivInst)` splits the current basic block into two blocks *at* the division instruction. The division and everything after it moves to the new `TailBB` block. The original `MBB` now ends at the point right before where the division was.

3. **Insert a conditional branch**: `B.bcnd(CC0::NE0, DivInst->getOperand(2).getReg(), TailBB)` inserts a "branch if not equal to zero" instruction. Operand 2 of the division instruction is the divisor. If the divisor is NOT zero, we branch to `TailBB` (where the division happens safely).

4. **Insert a trap**: `B.trap503(DivInst->getOperand(2).getReg())` — if we fall through (the divisor IS zero), we hit the trap instruction, which causes the CPU to raise trap 503.

5. **Increment the statistic counter**.

The control flow becomes:

```
Original MBB:
    ... (code before division)
    bcnd ne0, %divisor, TailBB    ; if divisor != 0, skip trap
    trap503 %divisor               ; divisor is 0 — trap!

TailBB:
    div %result, %dividend, %divisor  ; safe division
    ... (code after division)
```

#### runOnMachineFunction()

```cpp
bool M88kDivInstr::runOnMachineFunction(MachineFunction &MF) {
    const M88kSubtarget &Subtarget = MF.getSubtarget<M88kSubtarget>();
    TII = Subtarget.getInstrInfo();
    TRI = Subtarget.getRegisterInfo();
    RBI = Subtarget.getRegBankInfo();
    MRI = &MF.getRegInfo();
    AddZeroDivCheck = !TM->noZeroDivCheck();
    bool Changed = false;
    for (MachineBasicBlock &MBB : reverse(MF))
        Changed |= runOnMachineBasicBlock(MBB);
    return Changed;
}
```

Key points:
- All target information is extracted from the subtarget for the current function.
- `AddZeroDivCheck` is set based on the command-line option (note the negation — if `noZeroDivCheck()` returns true, we do NOT add checks).
- Basic blocks are iterated in **reverse order**. This is a common pattern when modifying basic blocks during iteration — iterating in reverse avoids issues with block splitting (since splitting creates a new block *after* the current one, which we'd visit later in forward order but have already passed in reverse order).
- The `Changed` variable tracks whether any modifications were made. If no divisions were found (or the pass was disabled), it returns `false`.

#### runOnMachineBasicBlock()

```cpp
bool M88kDivInstr::runOnMachineBasicBlock(MachineBasicBlock &MBB) {
    bool Changed = false;
    for (MachineBasicBlock::reverse_instr_iterator I = MBB.instr_rbegin();
         I != MBB.instr_rend(); ++I) {
        unsigned Opc = I->getOpcode();
        if ((Opc == M88k::DIVUrr || Opc == M88k::DIVSrr) && AddZeroDivCheck) {
            addZeroDivCheck(MBB, &*I);
            Changed = true;
        }
    }
    return Changed;
}
```

This iterates through instructions in the basic block in **reverse order** (same reasoning — we're modifying the block as we iterate). For each instruction, it checks if the opcode is a division instruction AND whether the check is enabled. If both conditions are true, it calls `addZeroDivCheck()`.

### Demonstrating the Pass

Given this IR with a division by zero:

```llvm
target triple = "m88k-unknown-openbsd"

@dividend = dso_local global i32 5, align 4

define dso_local i32 @testDivZero() #0 {
  %1 = load i32, ptr @dividend, align 4
  %2 = sdiv i32 %1, 0
  ret i32 %2
}
```

Running `llc m88k-divzero.ll` produces assembly with `bcnd.n` and `tb0` instructions — the conditional branch and trap respectively. The `.n` suffix indicates the branch has a delay slot (the instruction after the branch executes before the branch takes effect, which is a common RISC feature).

Running `llc m88k-divzero.ll --m88k-no-check-zero-division` produces assembly **without** these checks, demonstrating that the command-line toggle works correctly.

## Part II: Integrating a New Target into the Clang Frontend

### Why Is This Needed?

Up to this point, the M88k backend can translate LLVM IR to machine code via `llc`. But users write C/C++ code, not LLVM IR. To compile C code for M88k, the Clang frontend needs to know about the target — its data layout, register names, predefined macros, type sizes, calling conventions, and more.

This integration touches multiple areas of the Clang codebase, organized into three layers: driver integration, ABI support, and toolchain support.

### Layer 1: Driver Integration

The "driver" is the part of Clang that processes command-line options, determines the target, and orchestrates the compilation pipeline.

#### Adding the va_list Kind (TargetInfo.h)

In `clang/include/clang/Basic/TargetInfo.h`, a new entry is added to the `BuiltinVaListKind` enum:

```cpp
M88kBuiltinVaList
```

This tells Clang how variadic arguments (`printf`, etc.) are implemented on M88k. The struct layout describes the `va_list` type: it has an integer tracking which argument we're on (`__va_arg`), a pointer to stack arguments (`__va_stk`), and a pointer to register-saved arguments (`__va_reg`). Each target has its own `va_list` layout because the calling convention differs.

#### Creating M88kTargetInfo (M88k.h and M88k.cpp)

A new class `M88kTargetInfo` is created in `clang/lib/Basic/Targets/M88k.h`, extending `TargetInfo`. This is Clang's primary interface for querying target-specific properties.

**Private members:**

```cpp
static const char *const GCCRegNames[];
enum CPUKind { CK_Unknown, CK_88000, CK_88100, CK_88110 } CPU = CK_Unknown;
```

- `GCCRegNames`: An array of register name strings (r0–r31). These names are used for inline assembly constraints.
- `CPUKind`: An enum representing the three CPU variants in the M88k family. The default is `CK_Unknown`.

**Public methods (declarations):**

- `getTargetDefines()`: Provides the target-specific `#define` macros (like `__m88k__`).
- `getTargetBuiltins()`: Returns built-in functions the target supports (stub for now).
- `getGCCRegNames()` / `getGCCRegAliases()`: Register names for inline assembly.
- `getBuiltinVaListKind()`: Returns `M88kBuiltinVaList`.
- `hasFeature()`: Checks if a named feature is supported.
- `validateAsmConstraint()`: Validates inline assembly constraints.
- `isValidCPUName()` / `setCPU()` / `fillValidCPUList()`: CPU name validation and selection.

**The LLVM_LIBRARY_VISIBILITY attribute:** This is applied to the class to limit its symbol visibility. When building Clang as a shared library, this ensures `M88kTargetInfo` is only visible within the library — external code can't directly access the class. This is a standard practice for internal implementation classes.

**Constructor implementation (M88k.cpp):**

The constructor sets up the data layout string:

```cpp
std::string Layout = "";
Layout += "E";                // Big endian
Layout += "-m:e";             // ELF mangling
Layout += "-p:32:32:32";     // 32-bit pointers, 32-bit aligned
Layout += "-i1:8:8-i8:8:8-i16:16:16-i32:32:32-i64:64:64";  // Natural alignment
Layout += "-f32:32:32-f64:64:64";  // Float alignment
Layout += "-a:8:16";         // Aggregate alignment: 8 ABI, 16 preferred
Layout += "-n32";            // Native integer width: 32-bit
resetDataLayout(Layout);
```

Note the comment says "M68k is Big Endian" — this appears to be a typo in the book (should say M88k). The data layout string must match exactly what the backend expects (as defined in `computeDataLayout()` in the backend's `M88kTargetMachine.cpp`). A mismatch would cause verification failures.

The constructor also sets type mappings:

```cpp
IntMaxType = SignedLongLong;    // intmax_t is long long
Int64Type = SignedLongLong;     // int64_t is long long
SizeType = UnsignedLong;        // size_t is unsigned long
PtrDiffType = SignedInt;         // ptrdiff_t is signed int
IntPtrType = SignedInt;          // intptr_t is signed int
```

These affect how standard C types map to the target's actual types.

**CPU selection:**

```cpp
bool M88kTargetInfo::setCPU(const std::string &Name) {
    CPU = llvm::StringSwitch<CPUKind>(Name)
              .Case("generic", CK_88000)
              .Case("mc88000", CK_88000)
              .Case("mc88100", CK_88100)
              .Case("mc88110", CK_88110)
              .Default(CK_Unknown);
    return CPU != CK_Unknown;
}
```

`llvm::StringSwitch` is a utility that works like a switch statement on strings. It maps string names to `CPUKind` enum values. "generic" maps to `CK_88000` (the base model). If the name doesn't match anything, `CK_Unknown` is returned and the function returns `false` (indicating invalid CPU).

**Valid CPU enforcement:**

```cpp
static constexpr llvm::StringLiteral ValidCPUNames[] = {
    {"generic"}, {"mc88000"}, {"mc88100"}, {"mc88110"}};

void M88kTargetInfo::fillValidCPUList(SmallVectorImpl<StringRef> &Values) const {
    Values.append(std::begin(ValidCPUNames), std::end(ValidCPUNames));
}

bool M88kTargetInfo::isValidCPUName(StringRef Name) const {
    return llvm::is_contained(ValidCPUNames, Name);
}
```

These functions work together: `ValidCPUNames` is the authoritative list, `fillValidCPUList` populates a vector for error messages ("valid CPU names are: ..."), and `isValidCPUName` checks membership.

**Target-specific preprocessor macros:**

```cpp
void M88kTargetInfo::getTargetDefines(const LangOptions &Opts,
                                       MacroBuilder &Builder) const {
    Builder.defineMacro("__m88k__");
    Builder.defineMacro("__m88k");
    switch (CPU) {
    case CK_88000: Builder.defineMacro("__mc88000__"); break;
    case CK_88100: Builder.defineMacro("__mc88100__"); break;
    case CK_88110: Builder.defineMacro("__mc88110__"); break;
    default: break;
    }
}
```

When you write `#ifdef __m88k__` in C code, it works because of this function. The CPU-specific macros (e.g., `__mc88110__`) allow code to detect the specific CPU variant at compile time — useful for conditionally enabling features that only exist on certain models.

**Register names:**

```cpp
const char *const M88kTargetInfo::GCCRegNames[] = {
    "r0", "r1", "r2", ..., "r31"};
```

These are the names users can use in inline assembly (e.g., `asm("and %r2, %r3, %r4")`). Note: there's a typo in the text where register 30 is listed as `"r39"` instead of `"r30"`.

**Inline assembly constraint validation:**

```cpp
bool M88kTargetInfo::validateAsmConstraint(
    const char *&Name, TargetInfo::ConstraintInfo &info) const {
    switch (*Name) {
    case 'a': // address register
    case 'd': // data register
    case 'f': // floating point register
        info.setAllowsRegister();
        return true;
    case 'K': // the constant 1
    case 'L': // constant -1^20 .. 1^19
    case 'M': // constant 1-4
        return true;
    }
    return false;
}
```

When a user writes inline assembly with constraints like `asm("add %0, %1, %2" : "=d"(result) : "d"(a), "d"(b))`, this function validates that `d` is a valid constraint and configures it (here, `setAllowsRegister()` means the constraint accepts a register). The constant constraints (`K`, `L`, `M`) represent specific immediate value ranges that certain instructions can accept.

#### Options.td Changes

In `clang/include/clang/Driver/Options.td`, the M88k feature group and CPU flags are defined:

```tablegen
def m_m88k_Features_Group: OptionGroup<"<m88k features group>">,
                           Group<m_Group>, DocName<"M88k">;
def m88000 : Flag<["-"], "m88000">, Group<m_m88k_Features_Group>;
def m88100 : Flag<["-"], "m88100">, Group<m_m88k_Features_Group>;
def m88110 : Flag<["-"], "m88110">, Group<m_m88k_Features_Group>;
```

This means users can pass `-m88000`, `-m88100`, or `-m88110` to Clang to select the CPU. The `OptionGroup` organizes these flags under the "M88k" documentation group. `Group<m_Group>` makes them part of the `-m` family of machine-specific options.

### Layer 2: ABI Support

ABI (Application Binary Interface) support tells Clang's code generator how to produce LLVM IR that follows the target's calling conventions.

#### Code Generation Target Info (TargetInfo.h and M88k.cpp)

A prototype is added to `clang/lib/CodeGen/TargetInfo.h`:

```cpp
std::unique_ptr<TargetCodeGenInfo> createM88kTargetCodeGenInfo(CodeGenModule &CGM);
```

The implementation in `clang/lib/CodeGen/Targets/M88k.cpp` creates two classes:

**`M88kABIInfo`**: Extends Clang's `ABIInfo` class. For now, it's minimal — `computeInfo()` is empty and `EmitVAArg()` just returns the address. These would need real implementations for a production compiler (especially `EmitVAArg` for variadic function support).

**`M88kTargetCodeGenInfo`**: Extends `TargetCodeGenInfo`. It uses `DefaultABIInfo` for the basic calling convention logic, which handles simple cases (pass integers in registers, pass structs on the stack, etc.) without target-specific customization.

#### Teaching Clang About Acceptable Triples (Targets.cpp)

In `clang/lib/Basic/Targets.cpp`, a case for `m88k` is added:

```cpp
case llvm::Triple::m88k:
    switch (os) {
    case llvm::Triple::OpenBSD:
        return std::make_unique<OpenBSDTargetInfo<M88kTargetInfo>>(Triple, Opts);
    default:
        return std::make_unique<M88kTargetInfo>(Triple, Opts);
    }
```

This tells Clang that `m88k-openbsd` is a valid target triple. For OpenBSD, it wraps `M88kTargetInfo` in `OpenBSDTargetInfo`, which adds OS-specific defaults (like section naming conventions, default libraries, etc.). For other operating systems, the base `M88kTargetInfo` is used.

### Layer 3: Toolchain Support

The toolchain layer connects Clang's driver to the actual compilation tools (assembler, linker, etc.) and handles CPU/feature selection from command-line options.

#### M88k.h (ToolChains/Arch)

This header declares:

- **`FloatABI` enum**: `Invalid`, `Soft`, `Hard`. Soft float means floating-point operations are emulated in software (for CPUs without an FPU or for maximum portability). Hard float uses the hardware FPU.
- **`getM88kFloatABI()`**: Determines the float ABI from command-line options.
- **`getM88kTargetCPU()`**: Gets the CPU name from `-mcpu=` or the `-m88000`/`-m88100`/`-m88110` flags.
- **`getM88kTuneCPU()`**: Gets the tune CPU from `-mtune=`.
- **`getM88kTargetFeatures()`**: Collects target features into a vector.

#### M88k.cpp (ToolChains/Arch) Implementation

**CPU name normalization:**

```cpp
static StringRef normalizeCPU(StringRef CPUName) {
    if (CPUName == "native") {
        StringRef CPU = std::string(llvm::sys::getHostCPUName());
        if (!CPU.empty() && CPU != "generic")
            return CPU;
    }
    return llvm::StringSwitch<StringRef>(CPUName)
        .Cases("mc88000", "m88000", "88000", "generic", "mc88000")
        .Cases("mc88100", "m88100", "88100", "mc88100")
        .Cases("mc88110", "m88110", "88110", "mc88110")
        .Default(CPUName);
}
```

This function canonicalizes various CPU name spellings to a single standard form. Users might write `m88100` or `88100` or `mc88100` — all of these map to `mc88100`. The `native` keyword detects the host CPU (useful when compiling on actual M88k hardware).

**`getM88kTargetCPU()`**: Maps Clang's option IDs (e.g., `OPT_m88000`) to LLVM's canonical CPU names (e.g., `"mc88000"`). This bridges the gap between the frontend's option parsing and the backend's CPU naming.

**`getM88kTuneCPU()`**: Simply normalizes whatever `-mtune=` value was provided.

**`getM88kFloatABI()`**: Checks for `-msoft-float` or `-mhard-float`. If neither is specified, defaults to `Hard` (hardware floating point). This is the right default for M88k since both the MC88100 and MC88110 have FPUs.

**`getM88kTargetFeatures()`**: Currently only handles the float ABI — if soft float is requested, it pushes `"-hard-float"` to the features vector (disabling the hard-float feature). The text notes that M88k currently only supports hard float in this implementation.

## Part III: Targeting a Different CPU Architecture (Cross-Compiling)

### What Is Cross-Compiling?

Cross-compiling is the process of compiling code on one system (the **host**) to run on a different system (the **target**). This is essential for:
- Small embedded devices (like Raspberry Pi) that are too slow to run a compiler.
- Platforms where no compiler exists natively.
- Building for multiple architectures from a single development machine.

### Target Triples

Systems are identified by **triples** — configuration strings with the format:

```
<architecture>-<vendor>-<operating_system>[-<environment>]
```

Examples:
- `x86_64-pc-win32` — 64-bit x86 Windows
- `aarch64-unknown-linux-gnu` — ARMv8 Linux with GNU environment
- `m88k-unknown-openbsd` — M88k OpenBSD

Parts can be omitted when they're unknown or irrelevant: `aarch64-linux-gnu` is equivalent to `aarch64-unknown-linux-gnu`.

### Common Portability Pitfalls

When cross-compiling, your code must be portable. Three major issues:

1. **Endianness**: x86 is little-endian; M88k, SPARC, and some ARM modes are big-endian. If your code makes assumptions about byte order (e.g., casting a pointer to access individual bytes of a multi-byte value), it will break.

2. **Pointer size**: Pointers are 32 bits on M88k but 64 bits on x86_64. Using `int` to store a pointer will silently truncate on 64-bit systems (or be unnecessarily wide on 32-bit). Use `intptr_t` or `uintptr_t` instead.

3. **Type differences**: `long double` is 64-bit on ARM, 80-bit on x86, 128-bit on AArch64, and uses double-double arithmetic on PowerPC. Code that assumes a specific precision or size for `long double` will behave differently across targets.

### What You Need for Cross-Compiling

Three things are required:
1. A **compiler** that generates code for the target (like `aarch64-linux-gnu-gcc-12`).
2. A **linker** that produces binaries for the target (like `aarch64-linux-gnu-ld`).
3. **Header files and libraries** for the target (installed under `/usr/aarch64-linux-gnu/`).

On Ubuntu/Debian, these can be installed as packages:

```bash
$ sudo apt -y install gcc-12-aarch64-linux-gnu \
    g++-12-aarch64-linux-gnu binutils-aarch64-linux-gnu \
    libstdc++-12-dev-arm64-cross
```

The files are installed under `/usr/aarch64-linux-gnu/`, which serves as the **sysroot** — the logical root directory of the target system containing `bin/`, `lib/`, and `include/` directories.

**Note for other distributions**: Fedora and similar distributions may only provide cross-compiling support for bare-metal targets (like building kernels). If header and library files for user-space applications are missing, you can copy them from the target system. If no cross-toolchain is available at all, you must build GCC from source configured for the target.

### The TableGen Problem

LLVM uses `llvm-tblgen` during the build process to generate C++ code from `.td` files. When cross-compiling, everything is compiled for the *target* — including `llvm-tblgen` itself. But `llvm-tblgen` needs to *run* on the *host* during the build.

Solution: Build `llvm-tblgen` for the host first:

```bash
$ mkdir build-host
$ cd build-host
$ cmake -G Ninja \
    -DLLVM_TARGETS_TO_BUILD="X86" \
    -DLLVM_ENABLE_ASSERTIONS=ON \
    -DCMAKE_BUILD_TYPE=Release \
    ../llvm-project/llvm
$ ninja llvm-tblgen
$ cd ..
```

This creates a host-native `llvm-tblgen` binary that can run during the cross-compilation build.

### The Cross-Compilation CMake Command

```bash
$ mkdir build-target
$ cd build-target
$ cmake -G Ninja \
    -DCMAKE_CROSSCOMPILING=True \
    -DLLVM_TABLEGEN=../build-host/bin/llvm-tblgen \
    -DLLVM_DEFAULT_TARGET_TRIPLE=aarch64-linux-gnu \
    -DLLVM_TARGET_ARCH=AArch64 \
    -DLLVM_TARGETS_TO_BUILD=AArch64 \
    -DLLVM_ENABLE_ASSERTIONS=ON \
    -DLLVM_EXTERNAL_PROJECTS=tinylang \
    -DLLVM_EXTERNAL_TINYLANG_SOURCE_DIR=../tinylang \
    -DCMAKE_INSTALL_PREFIX=../target-tinylang \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_C_COMPILER=aarch64-linux-gnu-gcc-12 \
    -DCMAKE_CXX_COMPILER=aarch64-linux-gnu-g++-12 \
    ../llvm-project/llvm
$ ninja
```

Each option explained:

- **`CMAKE_CROSSCOMPILING=True`**: Tells CMake we're cross-compiling. This changes several CMake behaviors — for instance, it won't try to run compiled test programs (since they're for the wrong architecture).

- **`LLVM_TABLEGEN=../build-host/bin/llvm-tblgen`**: Points to the host-built `llvm-tblgen`. Without this, CMake would try to use the target-built version (which can't run on the host).

- **`LLVM_DEFAULT_TARGET_TRIPLE=aarch64-linux-gnu`**: The default triple for the resulting compiler. When you run the cross-compiled `llc` or `clang`, it will default to generating AArch64 code.

- **`LLVM_TARGET_ARCH=AArch64`**: Used specifically for JIT code generation. Normally defaults to the host architecture, but for cross-compiling, it must be set to the target.

- **`LLVM_TARGETS_TO_BUILD=AArch64`**: Which code generators to include. Must include at least the target architecture.

- **`CMAKE_C_COMPILER`/`CMAKE_CXX_COMPILER`**: The cross-compilers. These are prefixed with the target triple (e.g., `aarch64-linux-gnu-gcc-12`). CMake can't auto-detect cross-compilers.

### Verification

After building, you can verify the output:

```bash
$ file bin/tinylang
```

The output should indicate an ELF 64-bit executable for the ARM AArch64 architecture — confirming that cross-compilation produced a binary for the target, not the host.

### Cross-Compiling with Clang

The chapter notes that while Clang can naturally generate code for multiple targets (since LLVM supports multiple backends), it doesn't provide everything needed for cross-compilation — notably the C library is missing. You must mix LLVM and GNU tools.

Minimum Clang options for cross-compiling:
- `--target=<target-triple>`: Enables code generation for the target.
- `--sysroot=<path>`: Sets the root directory for target headers and libraries.
- `-I`: Additional header search paths.
- `-L`: Additional library search paths.

Common problems include picking up the wrong (host) header files and link failures due to missing or differently-named target libraries.

## Final Synthesis

This chapter ties together the complete M88k compiler story:

1. **Machine function passes** extend the backend beyond instruction selection. The `M88kDivInstr` pass demonstrates the complete pattern: declare the pass interface, register it with the target machine's pass pipeline, implement the transformation logic (scanning for division instructions and inserting conditional branches + traps), provide a command-line toggle, and integrate with the build system. This is a template you can follow for any post-instruction-selection transformation — peephole optimizations, instruction scheduling tweaks, hardware workarounds, etc.

2. **Clang frontend integration** connects the backend to the real world. Users don't write LLVM IR; they write C code. The integration spans three layers: the driver (command-line options, target triples, CPU selection), the ABI (how C types and calling conventions map to machine-level details), and the toolchain (connecting to assemblers, linkers, and library paths). Each layer requires specific classes and registrations, but the pattern is consistent across all LLVM targets — study any existing target (like ARM or MIPS) for a complete reference.

3. **Cross-compiling** is the practical reality of embedded and multi-platform development. The key insight is that building a cross-compiler requires a two-phase process: first build the host tools (`llvm-tblgen`), then build everything else with the cross-compiler. The CMake configuration must explicitly specify the cross-compiler, target triple, and host TableGen path. Portability issues (endianness, pointer sizes, type differences) are real concerns that must be addressed in your code.

Together, these three topics complete the journey from LLVM IR to a usable compiler: you have a backend that generates correct machine code (Chapters 11–12), custom passes that handle target-specific concerns (this chapter, Part I), a frontend that accepts C code (this chapter, Part II), and the ability to build for any target from any host (this chapter, Part III).
